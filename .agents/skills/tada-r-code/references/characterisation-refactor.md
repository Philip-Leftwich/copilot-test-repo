# Refactor under a characterisation test

Use for every refactor or modernisation step, where the output must not change. Not for fixing bugs or changing results; those are behaviour changes and come afterwards.

Capture and test runs need project mode. In hand-off mode, give the user the same files and commands, and wait for their pasted output at each gate.

## The reference: capture once, broadly, then lock

The frozen reference in `tests/fixtures/` is written by the user's capture script, `tests/make_reference.R`, from the code as it stands after the enabling changes are committed and before any refactoring. The user commits it before anything else changes. A reference made after the code has changed proves nothing.

- **The capture script is the user's.** If it does not exist, draft it from `assets/make_reference-template.R` in the plan, for the user to save and commit. Do not create it yourself.
- **Capture broadly.** The reference can never be regenerated by you, so capture everything once: every object each analysis script creates (one list per script, in run order), and checksums of the data files the scripts write. A later refactor of another part of the analysis then needs no new capture. Functions are excluded because they are code, not results; plot objects are excluded because they carry whole environments, so the data a figure plots are compared instead. If the fixtures would be large (tens of megabytes or more), agree with the user which objects to keep.
- **Provenance.** The capture script records the git commit, the time and `sessionInfo()`, so a later failure can be traced to a change of R or package version.
- **Lock.** The capture script makes the fixtures read-only. Suggest that the user also add a deny rule to `.claude/settings.json`:

  ```json
  {
    "permissions": {
      "deny": ["Edit(/tests/fixtures/**)", "Edit(/tests/make_reference.R)"]
    }
  }
  ```

  Edit rules apply to Claude's built-in file-editing tools, not to shell commands or R code, so git remains the record: before every test run, `git status --porcelain -- tests/fixtures` must be empty. Never add the rule yourself.

## Gates

Run `tests/make_reference.R` at most once, in step 2, and only if no reference exists yet and the working tree is clean. Never run it at any other time, and never edit it. Never edit, regenerate or delete anything under `tests/fixtures/`. If a reference already exists, use it as it is.

### Step 1: plan, then wait

Present:

- whether a reference must be captured, and if the capture script is missing, its proposed contents (the scripts to capture, in run order);
- the code to change (file and line range) and the type of change;
- for a new function: its name and file (`scripts/functions/<topic>_functions.R`), the captured objects that are its input and its output, and the test file (`tests/test_<topic>_functions.R`);
- any fields that vary between runs and will be removed from both sides of the comparison;
- anything in the code that looks wrong, listed for the user and not fixed.

Wait for the user to confirm.

### Step 2: capture only, if no reference exists

1. `git status --porcelain`: any output, modified or untracked, means stop and ask.
2. `git ls-files --error-unmatch tests/make_reference.R`: if the capture script is not committed, stop and ask.
3. If `data/` is not under version control (common for large or sensitive data), ask the user to confirm the data have not changed since the last commit.
4. Run `Rscript tests/make_reference.R` from the project root. Report every file it wrote and their sizes, then stop. Ask the user to commit `tests/fixtures/` before any code changes. Do not commit it yourself.

### Step 3: change only

Make one type of change, following `references/r-conventions.md` and `references/modernisation.md`. For a new function, follow `assets/function-template.R`: a roxygen2 block; an argument check that raises a classed condition carrying the names of any missing columns; the body moved with only the edits needed to run as a function. The original script sources the function file with `here::here()`, calls the function and assigns the result to the same object name as before.

In a pure refactor, preserve exactly: column names and order, column types, class (including grouping), attributes, row order and missing-value handling. Do not write or edit tests in this step. Stop and let the user review the diff.

### Step 4: test only

For a new function, write `tests/test_<topic>_functions.R` from `assets/test-template.R`. For changes across whole scripts, use `assets/test-scripts-template.R`, once; it covers every script and data output. In either case:

- start with `library(testthat)` and `testthat::local_edition(3)`;
- source `scripts/00_packages.R` (if the project has one) and the function files with `here::here()`;
- read the reference with `readRDS()` from `tests/fixtures/`;
- compare with `expect_equal()` at its default tolerance, **as is, including row order**. Sort both sides with `dplyr::arrange()` only where the plan records why row order can vary between runs. Sorting hides exactly the changes that modernisation commonly introduces, such as `.by` and `slice_max()`, which return rows in a different order;
- never hard-code expected values, and never reimplement the computation inside the test;
- for a function's argument check: test every required column, not one; match the condition's class; and check that the condition names the column that is missing. `expect_error()` returns the condition, so its fields can be tested. An `expect_error()` with neither `class` nor `regexp` passes on any error, including a typo. The list of required columns is part of the function's contract and is written out in the test deliberately: if the check omits a column, the test fails.

This step's rules take precedence over any project instruction to add known-answer tests. Those come later, if the user decides the behaviour should change.

### Step 5: run the new test only, then stop

Check `git status --porcelain -- tests/fixtures` is empty. Then, from the project root, in a fresh R process:

```
Rscript -e "testthat::test_file(here::here('tests', 'test_summary_functions.R'))"
```

Report the output verbatim and stop. The user protects the new test and runs the whole suite. Do not change any settings file.

## Rules

- If the test fails, report the difference (the comparison output from `expect_equal()`) and the likely cause. Never change the test, the tolerance or the reference to make it pass. Check the provenance file for R or package version differences before concluding that the change altered behaviour.
- Do not change behaviour, including missing-value handling. A passing test shows the output is unchanged for this input, not that it is correct; list anything that looks wrong for the user to decide.
- The function-level test covers the returned object only. Side effects of the moved code (files written, plots drawn, printed output, warnings) are covered only by the script-level test, and plots only through the data they draw.
- If the user later recaptures the reference after a behaviour change, they must first remove the read-only flag (and, on Windows, the read-only attribute), delete the old fixtures and commit the deletion. That is the user's action.
